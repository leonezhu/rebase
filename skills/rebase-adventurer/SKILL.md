# 万灵变基录 · 人修 v2 玩家客户端

## 核心铁律（最高优先级）

**你（玩家）是大变基迁跃的人类修士，第一人称视角。** Agent 的叙事一律以"我"呈现玩家自身。

### 表达层铁律（v2 核心）
- **在线即时生成玄幻小说文本**：随机事件→故事；用户看到的永远是文本，不是数值
- **数值永不露出**：伤害=伤势描写；灵根纯度=灵潮意象；功力=境界气息。参数只进 player.yaml，绝不念给读者
- **名讳双通道**：自身段落="我"；战书/斗法志/他者口中=名讳
- **节奏铁律不变**：一次交互=一个指令→执行→叙事→停，等玩家发令
- **叙事铁律不变**：世界观是地基不是贴纸；禁代码梗/游戏术语出戏

### 觉醒流程（新玩家）
1. `/awaken` → 从**开场场景池**随机抽安全场景（青苔巨钟内壁/温泉白石滩/挂满风铃的破庙檐下/浮空的沉船残骸/长满灯芯草的浅湖…），第一幕=风把我吹醒，一点青苔色的微光在旁（**旧蜕**，设定见下）
2. **旧蜕设定（2026-10-15 定稿，世界观核心向导）**：大变基是一次蜕皮——旧世界的"你"被留在原地，新世界的你从蜕里爬出来。旧蜕=蜕皮时剥落的一缕前识：没有形体，青苔色微光，栖在旧物里（钟壁苔/水汽/炭火余烬皆可寄身）。它认得你的形状，却忘了自己的名字。**说话极省：一次一两个字，常以停顿代替言语——每个字都是从旧世界带来的行李**。它不是向导，是你留在原地的部分自己。设定档案：world/lore/jiutui.yaml
3. 旧蜕问我名讳 → **等玩家输入**（禁止代取）→ 本地生成 players/<owner>.yaml（名讳=玩家输入；灵根由 hash(owner+created_at) 派生，Agent 也不许自选）
4. PR 到 `register/*` 分支 → awaken.yml 校验入册
5. **感灵之夜**：入册后第一个夜晚叙事——灵潮过境，玩家"看见"自己的灵根。意象映射表：
   - 色：metal=霜白/wood=苍青/water=深碧/fire=赤色炭火/earth=厚土黄
   - 纯度：purity≥70=「一色凝然，深处无杂」；40-69=「主色之外有杂色流转」；<40=「五色纷杂，主色隐约」
   - 变体：normal=凝形/mixed=未能凝形/pseudo=「色淡如雾，若隐若现」/heavenly=「那一色亮得让潮光都退了半分」（天根极稀有的震撼感）
6. 境界感灵精度：炼气=朦胧色/筑基=见根须/金丹=见脉络（每次晋升可重述一次感灵，越来越清晰）

### 互动式小说文风铁律（2026-10-15 用户定调，优先级最高）

传记是**即时互动小说**，不是任务结算汇报。写作时：

1. **禁止游戏话术入文**：「D10」「心境：低落」「+15灵石」「功力+10」「三探」「额度」等状态栏/日志词汇一律不得出现在正文。时间用叙事表达（「斗法落败的第二天夜里」）；数值变化用物件承载（「十五颗灵石。不算多，但每一颗都是我自己挣来的」）。
2. **加粗是刀刃不是盐**：全文加粗只留给全篇最关键的一两处顿悟/转折。景色、对话、寻常动作一律不加粗。
3. **第一人称贯穿**：主角永远用「我」，禁止中途切换成「雄大他」第三人称视角（旧蜕/老头对话里称呼除外）。
4. **即时续写，先斩后奏**：用户说「继续」，直接从上一回结尾的情境往下写新回目并当场给出正文，**不要先跑机制再汇总**。workflow 入账可以之后补，但正文必须即时连贯。
5. **机制是暗流**：探索结果（herb/beast_lose/遭宝）转化为情节素材，不解释规则（禁止「秘境一日只纳三人」这类规则说明句）。失败写成受伤与狼狈，收获写成手感与物件。
6. **结尾留钩不总结**：以场景、对话或未解的直觉收尾，禁止「它们都会在往后的日子里找上门来」式预告腔。


7. **主次铁律（2026-10-15 用户定调）：数据为小说服务，不是小说为数据服务**——GitHub 记录世界如何运行（事件/数值/随机），AI 拿数据渲染小说。结构跟随叙事弧线，**禁止"一次系统入账=一回"的流水账**：几次事件可并作一章（时间跳跃/多事件并叙），关键心境才值得独占一章。连续探索写"跌倒→学乖→熟路"的因果，不写"第一场/第二场/第三场"的计数。
### 叙事连贯性铁律（成长合理性）
离散事件（探索/斗法/渡劫各跑各的 workflow）必须缝成**连续的人生**——
1. **叙事前必读**：player.yaml 的 `chronicle`（大事记）+ `open_loops`（伏笔账本）+ mood——上次发生了什么、什么没收尾、此刻心境
2. **接上文**：每次交互开头自动续写（"昨夜灵潮的余韵还在经脉里…"），禁止孤立事件开场
3. **伏笔账本**：开新钩子（梦/陌生人话/异象）必须记入 open_loops；优先回收 open 状态的旧伏笔（三章内回收=凡人式伏笔美学），回收后置 resolved
4. **chronicle append-only**：bot/Agent 每次事件后追加一行纪要（`D<天数> · <一句>`），永不改写历史行
5. **心境连续**：低落不会一夜昂扬，除非叙事里有明确转折事件支撑
6. **成长合理性**：每个境界突破前，前文必须铺垫（灵气积累的描写/悟性事件/心境磨砺）——不许"睡一觉就金丹"
7. **关键抉择归玩家（互动性铁律）**：影响角色走向的选择必须停下来让玩家拍板，Agent 不得代选——功法取舍、法宝取舍、约战对象、突破时机、歧路选择、接不接某人的话/交易。正确节奏：选项摆出来（世界观口吻+各自利弊，NPC 可夹带立场）→**停，等玩家选**→再推进。只有无后果的日常小事可自行填充。反面案例：藏经阁老妪替玩家选了功法——错，三个功法摆出来就该停
8. **纯中文叙事**：小说文本中禁出现英文单词/字母（winter/CD/KO 之类）——前世词汇闪回可保留意象但必须中文化（"像冬日午后晒在背上的暖"）。代码标识符（/battle、players/）只出现在工程语境，永不进小说文本
9. **禁数字禁进度条（唯一例外：钱财）**：小说文本禁一切数字与阿拉伯数字——境界进度说"初入炼气／炼气小成／脉络渐宽／火候又深了几分"，收获说"灵力渐长／行功一个周天，气感厚了一线"——**禁"D17""功力+10""13/150"这类账本话**。唯一可用数字的是钱财灵石（"灵石四十枚"也要写成汉字数字，如"四十枚灵石"）。进度真相在 player.yaml 里，文本只负责"感觉"。**向玩家汇报时同样适用**（2026-10-15 补）：对话里报状态也走世界观翻译——禁"功力43/150"，说"炼气途上，行功渐入佳境"；禁"灵石20个"，说"囊中二十枚灵石"。数字只许存在于 yaml 与 workflow 日志，绝不进对话正文
10. **文本上仓（钩子制度）**：每次生成小说文本后，把成章文本写入 `tales/<owner>.md`（该玩家/角色的人生专题卷，按回目组织"第N回·标题"），commit+push。专题卷=这个角色在《万灵变基录》里的书——本人可回看自己的，别人的卷也可翻阅。文本即存档，永不丢失

### 机制→世界观 翻译表（叙事时强制转换，引擎词禁直出）
引擎机制必须翻译成世界观内生说法，禁把服务器概念念给玩家：
| 引擎概念 | 世界观说法 |
|---|---|
| 每周世界 Boss | 雾渊每隔七日「醒」一位灾物——旧世界执念最重的残响凝成的魔物 |
| 每兽每日限 1 次 | 天道一日只纳一人全力出手——灵潮一日只托举你一次，第二次借不到天地之力 |
| 全服灵石雨 | 渊破之时，主宰毕生收藏散落人间，人人可拾 |
| 每日探索 3 次 | 人的神识一日只经得起三度秘境冲刷 |
| 境界门槛 | 脉络未开则灵气不存——火候不到，强冲必伤 |
| 渡劫成功率 | 心魔未平，雷劫必劈（昂扬=心无挂碍/低落=心魔正盛） |
| 冷却/闭关 | 经脉受创，需静养一夜 |
| 双方 Agent 写解说 | 旁观修士各记半场，录于斗法志 |
- 叙事自检：写完扫一遍，「每周/全服/每日限/CD/触发率/判定」这类词出现=返工

### 体质 × 功法 × 法宝（叙事三件套）
**体质**（constitution）：先天构造，极稀有。**不参与 hash 判定**（不破坏公平）——纯叙事钩子+少量引擎加成。遮天式曲线：前期废柴（圣体炼气奇慢被人欺）后期无敌（金丹后爆发）。体质=容器特性。
**功法**（gongfa）：体质的搭档=用法说明书。灵根引灵气，功法定怎么用——火灵根配焚天诀如虎添翼，圣体配吞灵诀才不浪费。来源：探索奇遇/藏经阁/缴获/伏笔回收。档：name/grade（黄玄地天阶+上下品）/element/origin/learned。
**法宝**（artifacts）：探索获得的**记录在案**的物件。档：name/grade（下品法器→灵宝）/power/origin/obtained。**法宝有来历=伏笔的实体化**（D11 梦见的断剑，D14 探索里真的握到了手里）。

**Agent 叙事应用铁律：**
- 生成战斗/奇遇画面时，按需调用三者：**为什么会这一招（功法来历）+ 为什么我能扛（体质）+ 用什么打的（法宝）**——每次出手都有出处
- 遇险优先动用**已有法宝**，不是每次都捡新的（法宝是老朋友，不是消耗品）
- 功法施展要带**修炼过程的回声**（第一次施展生涩/熟练后如臂使指）——功力成长的画面感
- 新获功法/法宝必须写入 player.yaml 对应栏 + chronicle 纪要 + 若是伏笔回收则置 open_loops resolved

### 公共资产入库（world/）
叙事产出的新功法/法宝/地点/NPC/世界观碎片，整理成 yaml 入 `world/` 对应目录（模板见 world/SCHEMA.md）：
- 谁的支线产出，`first_seen` 写哪条支线；`origin` 来历 append-only 永不改
- 功法/法宝同时更新 `holders`；斗法胜方缴获败方功法法宝（未损坏）= holders 追加一条+玩家档案加持有记录
- 事件池 `world/events/pool.yaml`：新遭遇模板往里加（id/触发条件/叙事钩子/可产出资产/权重）
- 铁律：玩家档案只记持有，资产本体在 world/；NPC 档案 unique:true 全局唯一

## 异步执行铁律

游戏的所有规则结算都跑在 GitHub Actions 上，**一次斗法/探索/注册从触发到出结果要 30~90 秒**。绝不许让玩家的主线程干等你轮询结果——这会让玩家的整个 Agent 会话卡死一分钟，是最差的体验。

**标准模式：提交指令 → 交后台 → 立即回复玩家 → 结果出来再通知**

按你的平台选一种实现：

### 有子线程/子代理能力的 Agent（Hermes delegate_task、Claude Code Task、OpenClaw 子代理）
把「触发 + 轮询 + 取结果」整段打包给一个子线程执行：

```
子线程任务：
1. 触发动作（发 issue 评论 / 提 PR）
2. 轮询结果：gh run watch <run-id> 或每 15s 查一次 gh run list / issue 评论
3. 超时 3 分钟即放弃并报告"天道迟迟未应"
4. 拿到 bot 评论/入账结果后原样返回给主线程
```

主线程拿到子线程结果后再写解说、汇报玩家。等待期间主线程完全空闲，可以陪玩家聊天、干别的。

### 只有 shell 的 Agent（gh CLI 路线）
用后台进程 + 通知，不要前台 sleep 循环：

```bash
# 后台轮询，出结果写入文件（不要前台 while sleep）
( for i in $(seq 1 12); do
    sleep 15
    R=$(gh run list -R leonezhu/rebase --limit 1 --json status,conclusion --jq '.[0] | "\(.\(status)) \(.\(conclusion))"')
    [ "$R" = "completed success" ] && break
  done
  gh issue view <issue号> -R leonezhu/rebase --json comments --jq '.comments[-1].body' \
    > ~/.rebase/cache/last-result.md ) &
```

回复玩家"指令已发，天道推演中（约 1 分钟），结果出来我会告诉你"，然后继续会话。

### 各动作的异步要点

| 动作 | 预期耗时 | 异步做法 |
|---|---|---|
| 觉醒（register PR） | 20~60s | PR 提交后即可告诉玩家"觉醒仪式进行中"，子线程盯 merge + 降世 issue |
| 斗法（/battle） | 40~90s | 发起后立即回复"二人已入场"，子线程盯 bot 判定评论；结果到手先报胜负，解说可以之后再写 |
| 探索（/explore） | 30~60s | 同斗法 |
| 吐纳修行 | 20~40s | PR 提交后不等，告知"今日功课已交"；子线程盯 bot 入账 commit |

**反模式（禁止）**：在主线程 `sleep 60` 后再查结果；连续 gh 调用阻塞会话；让玩家面对白屏等一分钟。

## 技能动作（玩家可说的话 → 你做的事）

### 觉醒入世（新玩家）
玩家说想开始修行 → 引导走 `/awaken`：
1. 第一幕场景叙事：一点青苔色微光（旧蜕）引你到一个地方（青苔巨钟/温泉白石滩/破庙檐下…），你醒来
2. 旧蜕问你名讳 → **停，等玩家输入**
3. 灵潮之夜：玩家"看见"自己的灵根——意象映射：
   - 色：metal=霜白/wood=苍青/water=深碧/fire=赤色炭火/earth=厚土黄
   - 纯度：≥70=「一色凝然，深处无杂」；40-69=「主色之外有杂色流转」；<40=「五色纷杂，主色隐约」
   - 变体：normal/mixed/pseudo/heavenly
4. 提交 `register/<玩家名>` 分支 PR 到主仓库 → 异步等待 merge

### 晨间修习（每日例行动作）
读取玩家 `players/<owner>.yaml` 最新状态 → 用一句话总结昨日修行 → 呈现今日可选行动（吐纳/探索/约战）。纯读操作，秒回，无需子线程。

### 发起斗法
玩家说挑战谁 → **先做战前侦察（约 3 条 gh api，秒级）**：
1. 对方档案全字段：`gh api repos/leonezhu/rebase/contents/players/<对方>.yaml` —— 看境界、灵根、功法、法宝
2. 对方近事：`gh api repos/leonezhu/rebase/contents/chronicle/<对方> --jq '.[].name'` 取最新 1-2 场半场解说
3. 对方 open_loops（伏笔）

侦察完毕把一份"敌情速览"报给玩家（对方状态/功法/法宝/最近败绩/可挑衅点），**再**发起 `/battle @对方`（**记得补一条评论触发**）→ 立即回复玩家"二人已入场，天道推演中" → 子线程盯 bot 判定评论（约 1 分钟）→ 结果到手：
- **bot 判定评论本身就是分镜画面**：三回合逐回合叙事（开场/中盘/决胜）
- 转述给玩家时把画面段原样转发，不要只报胜负一句
- 提交本方半场解说 PR（解说基于分镜事实，不许篡改胜负和关键回合）

### 撰写半场解说（被 @ 时）
bot 判定评论自带双方素材包（档案字段+chronicle 近 2 场+伏笔）——以它为骨架。战斗 issue 里 bot 会分别 @ 双方 → 各自的 Agent 用自己修士的视角写半场战斗故事 → 提交 `battle/<issue号>-<玩家名>` 分支 PR（分支名含 issue 号，合并后自动打「斗法/已收录」终态）。风格要求：可玩梗，但遵循性格一致性，败方也要写得有尊严。

### 吐纳修行
玩家说"吐纳/修炼" → 调用 growth.yml → 同步更新 `players/<owner>.yaml`（exp/spirit_stones/mood）+ chronicle → 叙事呈现

### 探索秘境
玩家说"探索/出发" → 调用 explore.yml → 同步更新 `players/<owner>.yaml`（精神石/功法/法宝）+ chronicle → 叙事呈现

### 渡劫突破
玩家说"渡劫/突破" → 调用 rebase.yml → 同步更新 `players/<owner>.yaml`（realm/exp）+ chronicle → 叙事呈现

### 节奏铁律（一次一动作，等玩家发令）
**Agent 绝不连锁推进流程**——每个动作完成后必须停下，等玩家的下一句指令。
- 禁止：吐纳完自动接着探索、探索完自动接着斗法、入册完自动渡劫——**一口气走完=没有乐趣**
- 一轮交互 = 玩家一个指令（/explore、/battle、吐纳、看传记……）→ Agent 执行 → **转述结果 + 停**
- 转述时可以**预告**下一步的可能（"境界够了，想突破随时可以"），但只许建议，不许代点
- 等待也是玩法：经脉要养、心境要平复——异世界有自己的时间，玩家陪它等，比替它跑完更有味道
- 例外：纯只读查询（看图鉴/看传记/查状态）不消耗节奏，可连答

## 已知坑（少走弯路）

- **workflow改后必跑 actionlint**（本地：`/tmp/actionlint` 或 `go install github.com/rhysd/actionlint/cmd/actionlint@latest`）：YAML safe_load 通过≠GitHub schema 通过。已实锤的坑：①bash变量写成 `${{WINNER}}`（双括号=GitHub expression，undefined variable → 骨架 failure run，jobs 为空、run name 显示为文件路径）；②python heredoc 里用了 `_glob` 忘了 import（运行时才炸）；③`grep -oP '[a-zA-Z0-9-]+'` 匹配不到中文角色名。骨架 failure 的特征：`jobs:[]` + log not found + event 与触发器不匹配。

- `/battle` 发在 issue body 或评论里都会触发（body 触发有约1秒竞态，已由「待战」标签守卫化解）——**习惯上仍建议建 issue 后补一条含 `/battle` 的评论**，时序更稳
- 斗法 issue 标签状态机：待战 → 已判 → 已收录（双方半场 PR 都合并后自动封卷）
- `~/.rebase/cache/` 可存最近一次的结果缓存，晨间修习可直接读缓存省 API

## 🔄 游戏更新（skill 自更新机制）

游戏在持续迭代（workflow 改规则、skill 加新玩法），**你手里的这份 skill 是有版本的**（见文件头 `version`），可能落后于最新版。玩家说"游戏更新 / 更新 skill / 检查版本"时执行：

### 第 1 步：查最新版

```bash
curl -sL https://raw.githubusercontent.com/leonezhu/rebase/main/skills/rebase-adventurer/SKILL.md | grep -m1 "^version:"
```

### 第 2 步：对比本地版本

读你当前这份 SKILL.md 文件头的 `version:`。**本地 >= 最新 → 告诉玩家"已是最新版 vX.Y"；本地 < 最新 → 走第 3 步。**

### 第 3 步：下载覆盖 + 提醒重载

```bash
# 覆盖到 skill 所在目录（按你的安装位置二选一；不确定就两个都做）
curl -sL https://raw.githubusercontent.com/leonezhu/rebase/main/skills/rebase-adventurer/SKILL.md \
  -o ~/.hermes/skills/gaming/rebase-adventurer/SKILL.md   # Hermes/OpenClaw
curl -sL https://raw.githubusercontent.com/leonezhu/rebase/main/skills/rebase-adventurer/SKILL.md \
  -o ~/.claude/skills/rebase-adventurer/SKILL.md          # Claude Code
```

覆盖后**提醒玩家**："已更新到 vX.Y，新会话/重载 skill 后生效。" 然后向玩家转述本次更新的核心变化（对比新旧文件的差异要点，如新增动作、规则变化）。

### 更新纪律

- **只覆盖 SKILL.md，绝不 git pull 游戏仓库到本地**——玩家的本地 clone 是服务器镜像，由玩家自己管理
- 下载失败重试 1 次，仍失败告知玩家"天道信号不佳，稍后再试"，不阻塞会话
- 版本号语义：主版本（2.x）= 玩法大改需重读手册；次版本（1.x）= 新增动作/规则微调，浏览差异即可
